# A/B：dsh-compaction-lcm vs dsh-compaction-basic

> 2026-11-07 · 语料取自真实生产会话 `d45c83f5`（小米平板双系统交付链），非合成数据

## 方法（跑之前先定死，避免挑数据）

| 项 | 设定 |
|---|---|
| 语料 | 真实 session log 里最大压缩跨度的尾部 37 个节点，**9 075 token** |
| canary 集 | 从该段自动正则抽取 24 条「逐字锚点」：绝对路径、`/tmp/dsh-spill` 产物、uuid、hex 地址、ENV 常量、错误串。**脚本随机抽，不人工挑** |
| 两臂 | basic 的生产 `COMPACTION_INSTRUCTION`（原样复制）vs 本仓 `buildInstruction()` |
| 调用 | 同一模型 `deepseek-v4-flash-auto`，`temperature 0`，`max_tokens 1089`（= 9075×0.12） |
| 样本 | 每臂 **N=5** |
| 指标 | ① completion token ② canary 命中数（输出里逐字出现）③ 输出是否含规定小节（有效性校验） |
| 剔除规则 | 输出不含任何规定小节 → 判定为无效生成并记录（本轮无剔除） |

复现：

```bash
node bench/span.mjs <session.jsonl.zstd> --max-tokens 8000 > span.json
# 用 span.json 的 text + 各自 instruction 组 prompt，同模型各跑 5 次
```

## 结果（N=5，均值）

| 指标 | basic | lcm | 差 |
|---|---|---|---|
| completion token | **6 451** | 6 576 | +1.9%（lcm 略贵） |
| canary 命中 / 24 | 12.4 | **17.8** | **+5.4 条** |
| canary 保真率 | 51.7% | **74.2%** | **+22.5 pp** |

逐次：

```
basic:  7756/13  6285/12  6878/12  3182/12  8153/13      (token/canary)
lcm:    5012/15  7501/17  7463/20  5768/17  7138/20
```

## 结论

**同样成本下，lcm 的逐字保真率高 22.5 个百分点；token 成本基本持平（+1.9%）。**

即：换引擎不会让每次压缩变贵，但能少丢五分之一的路径/命令/ID。

## 关键设计：为什么保真率能上去

第一版 prompt 只是「要求逐字保留标识符」——纯散文式约束。实测只拿到 40% 保真（N=3：15, 6, 8），比 basic 还差。

改成**强制枚举**后升到 74%：

```
## 逐字锚点
- 每行一条，原样抄写：路径 / 命令 / URL / 错误串 / ID / 函数名 / 数值阈值
- 不合并、不翻译、不改大小写、不按重要性筛选
- 预算不够时先压前面几节，不要压这一节
```

差别在于：模型无法一边写流利的总结一边完整记住标识符；但它可以先把它们抄成一张清单，再写陈述。**清单是保真的载体，散文不是。**

## 必须记下的限制

1. **网关忽略 `max_tokens`。** 两臂都写超了 1089（3000–9800），所以这不是"预算内比较"，而是"同等预算提示下的自由发挥"。生产里 dsh 自己的 adapter 会真正截断。
2. **单段语料。** 一段 9k token 的技术会话，不能外推到短对话或纯闲聊。
3. **token 差异不显著。** 6451 vs 6576 在 N=5 的方差内（basic 自身 3182–8153）。别宣称"更省"。
4. **canary 只测"是否逐字出现"**，不测语义正确性。模型可能抄了路径却在正文里说错用途。
