# A/B 报告 v3 — 结论：不换

> 2026-11-07 第三版。v1 被审计推翻；v2 撤回并重做仪器；v3 给出重测数据与裁决。

## 0. 裁决

**不切换默认引擎。** 现有证据既不支持"lcm 的摘要更好"，也不支持"引擎有增益"——
两个语料上的方向相反，而唯一的 basicplus 数据点（只给 basic 加那一段锚点指令）
反而最高。**收益（如果有）跟的是那段 prompt 指令，不是引擎。**

## 1. 撤回记录（v1 的错误，全部作废）

## 4. 读这几张表要抓住的四件事

1. **方向不稳定。** c2 上 lcm +12.5pp，s 上 lcm −3.6pp。n=4/n=2 的样本撑不起"更好"。
2. **lcm 不是免费的。** c2 上它多写了 38% 的输出 token（7 912 vs 5 741）——枚举锚点本身就贵。
3. **basicplus 是唯一的归因线索，而现在它最高。** 如果这条成立，那增益来自"强制枚举"这段指令，任何 backend 加上都该有——与引擎无关。
4. **basicplus 在大语料上跑不完。** 强制枚举会把输出拉到 7–10k token，超过 MCP 工具 60s 上限；缩到 4.3k 语料才跑得通。这本身就是一条产品结论：**枚举策略的代价是输出长度，不是免费午餐。**

## 5. 所以按你的第 4 条要求：不换

"实测效果得比原版好才换" —— 现在没有一份能站住的对照数据说 lcm 更好。
**保持 basic 为默认引擎，插件留在仓库里作为可选 backend。**

真正能支撑"换"的实验还没做：用真实 `compile()` 跑 787 节点 / 436k tok 的生产跨度，
压缩后继续原任务，记完成步数与重读次数。那才是引擎级指标，而本报告全部是 prompt 级指标。

## 7. 引擎级实测（唯一能支撑"换"的那类证据）


### 为什么这条比前面的 prompt 对比重要

436k token 的跨度上，**任何摘要都装不下全部锚点** —— 生产摘要只留下 12.5%。
这不是模型不够好，是摘要本身的容量天花板。

- **摘要型 backend**：checkpoint 里有多少就是多少，12.5% 之后剩下的没了（模型侧没有指针）
- **本 backend**：checkpoint 里同样只有一部分，但每个 checkpoint 都带 `seq` 指针和
  RECALL 指南，`lcm_expand` 能把原文逐字取回 → 100%

**这才是架构差异，且不依赖任何 prompt 技巧。**

### 与此同时发现的真 bug

写这个测量时发现 `recall.js` 用 `session.events[seq]` 直接下标。持久化日志的**第一条是
没有 `seq` 的 header 记录**，于是每个 seq 都错位一格，每次 recall 都返回
`[seq N: not found in this session]`。

修复：新增 `src/events.js` 的 `resolveEventAt()`，优先用 session 自己的
`eventAt`，否则按事件自身的 `seq` 建索引（缓存）。`recall.js` / `search.js` 全部改用它。

回归测试在 `test/recovery.test.js`，其中包括一条**防空过**断言：若 recall 走了
raw-JSON fallback，子串永远能命中，测试就失去意义 —— 所以强制要求走 projection。

### 诚实的边界

basic 在大跨度上不是"0"：dsh 有 `session_search` 系列工具，模型**如果自己想起来去搜**
也能找回。差别在于：

- 本 backend 的 checkpoint **主动告诉模型怎么找**（RECALL 指南 + 每个条目的 `seq`）
- basic 的 checkpoint **什么也不说**，找回全靠模型自己想到

所以准确的表述是「**可发现的可恢复性** 12.5% → 100%」，而不是「basic 完全找不回」。

## 14. 检索质量：能不能"找到"被丢掉的事实

§7 证明的是"给定正确 seq，原文能逐字取回"。那是容易的一半。这一节测难的一半：
**agent 只记得一个字符串，丢进 `lcm_search`，能不能找到那个事件。**

**方法**（`bench/retrieval.mjs`，不调模型）：查询 = 被摘要丢掉的锚点本身；gold = 跨度内包含它的事件（`any` = 任一处，这是真实用法）；指标 recall@1/5/10、MRR、NDCG@10。

### 结果（修正仪器后，三份真实压缩日志）

| 日志 | 锚点 | 排序 | recall@1 | recall@5 | MRR | NDCG@10 |
|---|---|---|---|---|---|---|
| 1 `d45c83f5` | 21 | seq | 0.381 | 0.952 | 0.581 | 0.673 |
| | | score | 0.524 | 0.762 | 0.614 | 0.654 |
| | | **density** | **0.714** | 0.952 | **0.793** | **0.832** |
| 2 `65bd8898` | 22 | seq | 0.682 | 0.955 | 0.802 | 0.851 |
| | | score | 0.773 | 0.909 | 0.831 | 0.871 |
| | | **density** | 0.727 | 0.955 | **0.840** | **0.880** |
| 3 `d7951a68` | 24 | seq | 0.083 | 0.917 | 0.502 | 0.609 |
| | | score | 0.667 | 0.833 | 0.727 | 0.767 |
| | | **density** | **0.750** | **1.000** | **0.861** | **0.897** |
| 均值 | 67 | seq | 0.382 | 0.941 | 0.628 | 0.711 |
| | | score | 0.655 | 0.835 | 0.724 | 0.764 |
| | | **density** | **0.730** | **0.969** | **0.831** | **0.870** |

**结论：长度归一化密度胜出，已设为默认。** 三个日志的 recall@1 / MRR / NDCG@10 全部领先时间序（均值 +0.35 / +0.20 / +0.16），recall@5 持平或更高；对 score 只在日志 2 的 recall@1 上落后（0.727 vs 0.773），其余全胜。

**但不要写成"三份都显著"**：recall@1 的逐锚点翻转做精确二项检验 —— 日志 1 是 9:2（**p=0.065**，边缘）、日志 2 是 6:5（**p=1.0**，持平）、日志 3 是 18:2（**p=0.0004**）。也就是说这个默认排序的胜势在日志 1/3 站得住，在日志 2 上是"持平偏小胜"。

### 我这条结论曾经是反的（仪器 bug）

第一版结论写的是"相关性重排输了、默认保持时间序"。那是**仪器错**：`retrieval.mjs` 里 `rank = hitIndex + 1` 之后落盘又 `+1`，存的是 index+2，于是 **recall@1 恒为 0**（所有模式都一样），恰好抹掉了 density 在 rank-1 上的全部优势。同一处还把 NDCG 写成与 recall 恒等的假函数。

修正后：`rank` 只加一次；NDCG 改成真正的 `1/log2(rank+1)`；`at1 ≡ 0` 那个"首个命中总在跨度外"的归因也一并删除 —— 它本来就不成立。

**方向结论因此反转**，这是本轮最该记住的一条：一个错误的计数口径，足以让"最好的排序"看起来像"最差的排序"。

### 边界

- 标签 67 条，三份真实压缩日志，不是 held-out；三份的跨度来源见 `bench/results/retrieval-20261107.json`
- `gold=first` 口径下 density 反而差（日志 1：recall@1 0.143 vs seq 0.381）：密度会挑"整段都在讲这个词"的短事件，而不是"第一次出现"。真实用法要的是**任意一份**，所以默认按 `any` 优化；`first` 的数字一并留在这里
- 查询是精确字符串，不是自然语言

## 15. 等预算对比：这才是"不比原版差"的正确口径

§3 的消融让两臂**自由发挥**（网关忽略 `max_tokens`），所以"成本"从来不是受控变量，保真数字混了"压得更好"和"写得更多"。非劣性只有在**同一预算**下才有意义。

**方法**（`bench/equal-budget.mjs`）：两臂输出都截断到同一 token 上限（= 引擎自己的 `clamp(span×0.12, 512, 16384)`），再数逐字锚点。语料 s（4 302 tok，14 条锚点），预算 **516 tok**，temperature 0。

### 第一次测：我们输得很惨

| 臂 | 锚点 | 截断后 token |
|---|---|---|
| basic | 2/14 | 498 |
| **lcm** | **0/14** | 514 |

原因不是模型，是**我的小节顺序**：锚点清单排在最后，截断从尾部砍 —— 恰好砍掉了唯一承载保真的那一节。诊断证据：`/tmp/eqb-s-lcm-1.txt` 尾部停在 `## 逐字锚点\n- /vol3/1000/work/`。

### 修法：把锚点清单提到第一节

`SUMMARY_SKELETON` 改成 `逐字锚点 → 目标与约束 → 已完成 → 未决问题 → 下一步`，并在指令里写死"预算紧张先砍叙述，不要砍清单"。截断从此只损失散文。

### 修完重测（等预算，N=4/臂）

| 臂 | 各次命中 | 均值 | 截断后 token |
|---|---|---|---|
| basic | 2, 2, 3, 2 | **16.1%** | 494 |
| **lcm** | 3, 4, 4, 2 | **23.2%** | 509 |

**结论：同一预算下不比原版差（+7.1pp，方向一致 3/4 次）。** n=4 不足以下"更好"的结论，但足以支撑"不更差"，而这正是本包要守的线。

### 边界

- 单语料（4.3k tok 的小跨度）、单模型、N=4；没做配对检验
- 预算固定在 12% 比例，没做多预算点曲线
- 修前的 0/14 说明这条结论对**输出结构**高度敏感 —— 换个模板可能又翻车，所以 `SUMMARY_SKELETON` 顺序现在有单测守着

## 16. 换掉 MCP 通道与"不要设 max_tokens"

前两节的测量有两个仪器问题，这一节一并解决。

### 为什么不再走 MCP

之前所有模型调用都经过 agent 的 MCP 工具，它有两个副作用：
1. **约 60 秒硬截止** —— 大 prompt 直接被掐死，整个 basicplus 臂因此**零数据**；
2. **`max_tokens` 不被执行**（问 40，得 654），所以"等预算"从来不是真的等。

现在改成直接打 OpenAI 兼容 HTTP（`bench/llm.mjs`）：截止时间归我，凭证取环境或 `~/.dsh/.credentials.yaml`，脚本可独立跑。

### 但 `max_tokens` 是否执行取决于**路由**，不是通道

同一句请求、同样 `max_tokens: 40`：

| 模型 | 实际完成 | finish_reason |
|---|---|---|
| `best` → glm-5.3 | 40 | length |
| `balanced-lite` → agnes-3.0-flash | 40 | length |
| `deepseek-v4-flash-auto` → deepseek-v4.1-flash-1017 | **654** | stop |

所以之前"网关忽略 max_tokens"的结论只对 deepseek 那条路由成立。

### 两种比较都做了（语料 s，14 条锚点）

**A. 不设上限（自然长度）** —— 让两臂自由写，同时看保真与成本：

| 臂 | 各次命中 | 均值 | completion token | 锚点/1k token |
|---|---|---|---|---|
| basic | 5,5,5,5,5 | **5.0** | 2 700 | 1.85 |
| **lcm** | 5,5,5,5 | **5.0** | **2 182** | **2.29** |

**同样保真，少写 19% 的 token。**

**B. 生成期硬上限 516**（只有会执行 `max_tokens` 的路由才成立）：

| 臂 | 各次命中 | 均值 | token |
|---|---|---|---|
| basic | 4,1 | 2.5 | 516 |
| **lcm** | 3,4 | **3.5** | 516 |

**结论**：不设上限时保真打平、成本更低；设上限时同成本下保真更高。两个方向都不比原版差。

### 边界

- 用的是 `balanced-lite`(agnes-3.0-flash)，与 §15 的 deepseek 数字**不可跨表比较**
- N=4–5，无配对检验
- B 里 basic 的 4,1 方差很大，单点不可靠

## 17. 端到端：摘要还剩多少“逐字事实”

§15/§16 数的是**锚点在摘要文本里的出现次数**，那是文本属性。真正要回答的是：把摘要交给模型，模型还能不能把那些字面值**说出来**。这两件事不等价 —— 摘要可以带着一个路径，但模型复述时抄错一位就没了。

### 为什么按“类型分组”问

旧的 `qa-eval` 一个锚点问一次，且提示语里带 `near "<片段>"` 定位。实测：lcm 摘要**装进了 6 个锚点中的 5 个，得分却是 0/6** —— 因为摘要里没有那个定位片段，模型据此答了 UNKNOWN。

`bench/qa-recall.mjs` 改成按类型整组索要（“列出全部绝对路径 / 列出全部 0x 十六进制值 / …”）：不点名、不泄漏、也没有“定位不到”的歧义。

### 语料

`/tmp/c2.json`：真实会话跨度，1 193 个节点 → 渲染 31 条，32 259 字符（估 8 065 token），36 个 canary 去嵌套去重后 **24 条**。

### 结果（`balanced-lite`，输出上限 1 500，全臂撞顶）

| 臂 | 上下文 | 命中 | 命中率 | completion token |
|---|---|---|---|---|
| basic 摘要 | 5 283 字符 | 4/24 | **16.7%** | 375 |
| **lcm 摘要** | 8 175 字符 | 9/24 | **37.5%** | 1 500 |
| 全跨度（天花板） | 32 259 字符 | 10/24 | **41.7%** | 1 500 |

**读法**：模型从**整段原文**也只能说出 10 条 —— 那是模型侧的复用上限，不是摘要的锅。lcm 用 25% 的上下文拿到这个上限的 90%，是 basic 的 **2.25×**。

### 边界（这条不修饰）

- 三臂都撞 1 500 输出上限，所以 41.7% 这个“天花板”**是被 cap 压低的**，不是模型的真实上限；等预算口径下 lcm 的优势小于这张表
- 单跨度、单模型、每臂跑一次，没有方差估计
- 命中判据是子串匹配：模型把路径抄错一位即算未命中，这对**长路径占比高**的语料偏严格
- 与 §15/§16 的语料不同（s vs c2），**不可跨表比较**

## 18. §17 的天花板是被 cap 压出来的 —— 提高输出上限后重测

§17 三个臂全都撞 1 500 输出上限，所以那张表**不能**用来比较保真：它比的是谁在 1 500 token 里塞得更多。把上限提到 3 000 重跑（`MAX_TOKENS=3000`，`bench/qa-recall.mjs` 现在接受该环境变量并把 `finish_reason` 一并记下）：

| 臂 | 上下文 | 1 500 上限 | 3 000 上限 | finish_reason@3000 | completion token@3000 |
|---|---|---|---|---|---|
| basic 摘要 | 5 283 字符 | 4/24 = 16.7% | 4/24 = 16.7% | **stop** | 928 |
| **lcm 摘要** | 8 175 字符 | 9/24 = 37.5%（撞顶） | **16/24 = 66.7%** | **stop** | 1 977 |
| 全跨度 | 32 259 字符 | 10/24 = 41.7%（撞顶） | 4/24 = 16.7%（撞顶） | **length** | 3 000 |

### 三条各自不同的结论

1. **basic 从来不是被 cap 限住的**。它 928 token 就 `stop` 了 —— 16.7% 是它的真实上限，不是仪器上限。加预算对它毫无帮助。
2. **lcm 的 37.5% 才是被 cap 压出来的**。3 000 上限下它自己收尾（`stop`，1 977 token），命中翻到 66.7%，是 basic 的 **4 倍**。
3. **全跨度那一行现在不可用了**。3 000 不够把 32k 字符的原文逐项枚举完（`length`），截断点一漂，命中从 10 掉到 4 —— 这是提问方式与上限的耦合，不是原文比摘要差。要当真正的天花板，得给它单独一个更高的上限。

### 修订后的读法

§17 里那句「模型从整段原文也只能说出 10 条，那是模型侧的复用上限」**撤回**：那是 1 500 上限下的截断。目前**没有**一个可信的天花板数字，因为全跨度臂还没在足够高的上限下跑过一次。

可采信的只有一条：**在同一 3 000 上限、同一问法、同一模型下，lcm 摘要把 66.7% 的逐字事实交给了模型，basic 摘要交给它 16.7%**，且 lcm 是自然收尾。

### 边界

- 单跨度（c2）、单模型、每臂一次；16/24 vs 4/24 的差距大到不需要统计检验才敢说方向，但**没有**做重复
- 全跨度臂的天花板仍未测出，所以「摘要恢复了原文多少比例」这句话现在**不能**说
- 与 §15/§16 的语料不同（s vs c2），仍不可跨表比较

## 19. 保真只有一条口径：类型分组逐字召回（成本不再作为指标）

§15/§16 用「等预算」「自然长度 token 数」把成本当成了半边指标。**成本不是本包要守的线**，这条线撤掉之后，能支撑判决的只剩一个数：把摘要交给模型，它还能不能把那些字面值说出来。

### 仪器

`bench/summarize-arm.mjs` + `bench/qa-recall.mjs`。前者用**代码里的** `buildInstruction()` 现取指令（不再用烤进 prompt 文件的旧副本），后者按类型整组索要（不点名、不泄漏）。

### 结果（`balanced-lite`，输出上限 8 000，全部 `stop` 自然收尾）

| 语料 | 跨度 | basic 摘要 | **lcm 摘要** | 全跨度天花板 | lcm / 天花板 | basic / 天花板 |
|---|---|---|---|---|---|---|
| `s`（14 锚点） | 4 302 tok | 2/14 = 14.3% | **7/14 = 50.0%** | — | — | — |
| `c2`（24 锚点） | 8 065 tok | 4/24 = 16.7% | **15/24 = 62.5%** | **20/24 = 83.3%** | **75%** | 20% |

**天花板 20/24 的测法**：全跨度臂在 8 000 上限下用掉 3 374 token 就 `stop` 了 —— cap 不是约束，模型自己列完收尾。漏掉的 4 条是 3 个 UUID + `BASE_IMAGE`，属模型漏列，不是截断。所以没有再加额度的意义。

**结论：两个语料上 lcm 摘要的逐字保真都是 basic 的 3.0–3.5 倍，且达到模型对同一原文复用上限的 75%。** 这是本包唯一需要守的线，它守住了。

### 三条必须记下的仪器事实

1. **同一 prompt 重跑得到逐字节相同的回复**（网关缓存）。所以「跑 3 次取均值」在这套仪器上是假重复 —— 本节的 N 是 1，不是 3。所有 `s.json` 三臂的 3 次记录数值完全相同（basic 1560/1560/1560 等），不是稳定性证据。
2. **输出上限会改变命中数，方向还不单调**。`c2` 全跨度臂：1 500 上限 → 10/24，3 000 → 4/24，8 000 → 20/24。截断点漂移会让命中数上下跳，所以**跨上限的数字不可比**，只有「同一上限下的横向比较」和「`stop` 自然收尾时的绝对值」有意义。
3. **一次退化循环**：`lcm` 臂在 8 000 上限下有两次 `finish_reason=error`，末尾把 `(verification.json + root-build.json)` 重复 30+ 次。换标签重跑拿到干净样本，命中数不变（15/24）。这是模型侧退化，不是引擎 bug，但它说明**单次调用不能当结论**。

### 被这条口径推翻的一件事

我一度给摘要指令加了「后面四节合计不超过 20 行」去压成本。实测：`s` 语料 7/14 → **3/14**（掉一半）。原因是模型把「行数上限」读成了对整份回复的上限，连锚点清单一起削。**该上限已回滚**，`test/lcm.test.js` 里留了反向断言（`doesNotMatch(/不超过 \d+ 行/)`）防止再被加回来。

### 边界

- 两个语料、单模型、每臂一次有效调用（见仪器事实 1）
- 命中判据是子串匹配，长路径抄错一位即算未命中，对路径密集型语料偏严格
- `s` 语料没测全跨度天花板，所以那一行只有横向比较、没有「达到天花板多少」

## 20. LongMemEval_S：把原项目 METHODOLOGY 的 Layer 1 真的跑一遍

前面所有检索数字都来自**我们自己的**压缩日志（21–24 条锚点、2–3 份日志）。那能证明「被摘要丢掉的东西找得回来」，但证明不了「和原版 lcm 比谁强」—— 因为它连数据集都不是同一个。

这一节改用 lcm-x 的 `benchmarks/METHODOLOGY.md` 里写死的那套 Layer 1 口径：LongMemEval_S、pin 住的 revision、每题全新 store、查询 = 问题原文、不许挑关键词重试、session 级 recall@k / NDCG@10。

**数据**：`longmemeval_s`，revision `2ec2a557…`，278 025 796 B，sha256 `08d8dad4be43ee2049a22ff5674eb86725d0ce5ff434cde2627e5e8e7e117894`，**500 题全部有非空 `answer_session_ids`**。每題中位 50 个 session / 492 个事件。

### 结果一：按 METHODOLOGY 规定的查询，词面臂几乎全灭

| arm | sR@5 | sR@10 | sNDCG@10 | 零命中率 |
|---|---|---|---|---|
| seq | 0.002 | 0.002 | 0.001 | **99.8%** |
| score | 0.002 | 0.002 | 0.001 | 99.8% |
| density | 0.002 | 0.002 | 0.001 | 99.8% |

500 题里 **499 题零命中**。机制很直白：`searchSession` 是逐行正则，`What degree did I graduate with?` 这一整句只有当它逐字出现在某一行里才会命中 —— 而那恰好发生在 1 题上。排序模式救不了一个空候选集。

**这是真实的，不是仪器坏了**：`lcm_search` 的契约是「agent 记得一个字符串（路径、id、报错行），贴进去，拿回那个事件」。它从来不是问答检索器。

### 结果二：和 lcm-x 的 `fts` 臂用同一种查询构造，才有可比性

lcm-x 的 `fts` 臂也不是拿问题原文去搜的：它的 `build_fts_query` 会**分词、去停用词、把词 OR 起来**。把这套查询构造搬到我们这边（`tokenOr`），两个词面系统才站在同一起跑线上：

| arm | sR@5 | sR@10 | sNDCG@10 | sR@1 | MRR |
|---|---|---|---|---|---|
| seq | 0.300 | 0.502 | 0.178 | 0.062 | 0.191 |
| **score** | **0.774** | **0.874** | **0.602** | **0.470** | **0.604** |
| density | 0.626 | 0.826 | 0.431 | 0.148 | 0.348 |

**对照 lcm-x 自己的词面臂 `fts`：sR@5 0.20 / sR@10 0.36 / sNDCG@10 0.204。**

同口径下我们 **sR@5 0.774 vs 0.20**、**sR@10 0.874 vs 0.36**、**NDCG 0.602 vs 0.204**。

**至于为什么**：`score` 按事件内的命中行数排序，没有长度归一；SQLite FTS5 默认是 BM25（有长度归一和 IDF）。在「一个 session 几十个 turn」的 haystack 里，不做长度归一的那个反而更贴合 —— 但这是**观察到的现象，不是我验证过的机制**。要确认得把同一个分数函数分别实现到两边去测，我没做。

### 一个反直觉的发现：density 不是万能的

在**我们自己的**压缩日志上 density 是最优（§14，recall@1 0.730 vs 时间序 0.382）。在 LongMemEval 上 **score 明显更好**（0.774 vs 0.626），density 掉到和 seq 一个量级。

**最可能的解释**（未验证）：density 除以事件长度，而 LongMemEval 的证据单元是**整个 session（几十个 turn、上万字符）**，长度惩罚把承载证据的长事件压了下去，短而恰好提了一嘴的事件反而排前面。我们的日志里事件粒度细、命中密集，density 才有优势。

这条我没有单独做实验去证实 —— 它只是「两个数据集上方向相反」这个事实的一个合理猜测。要证实得把命中事件的长度分布和它们所属 session 是否为证据画出来。

**所以默认排序按场景分**：短事件、锚点式检索用 `density`（当前默认）；长文档/整 session 检索用 `score`。这不是妥协，是两个不同形状的问题。

### 与 lcm-x 嵌入臂的关系（不可直接比）

| lcm-x arm | sR@5 | sR@10 | 说明 |
|---|---|---|---|
| chunk_vectors | 0.96 | 0.98 | 对话块嵌入 KNN |
| summary_vectors | 0.87 | 0.93 | 每 session 一个摘要的嵌入 KNN |
| hybrid_rrf3 | 0.77 | 0.97 | FTS + summary + chunk 三路 RRF |
| hybrid_rrf | 0.49 | 0.64 | FTS + summary 两路 RRF |
| fts | 0.20 | 0.36 | **唯一无嵌入的臂** |

我们的 0.774 落在 `hybrid_rrf3`（0.77）和 `summary_vectors`（0.87）之间，**但那是纯词面的结果**，一个嵌入都没用。这不是「我们比他们的嵌入强」，是「他们的 fts 实现没把打分方式调对」。要说嵌入层面的强弱，得等向量臂跑完。

### 边界

- Layer 1 只测检索，不测端到端答题（那是 Layer 2，`bench/layer2-qa.mjs`）
- turn 级 unavailable：LongMemEval_S 只标到 session 粒度，逐 turn 标注不存在，编一个出来没有意义
- `maxSearchHits=200` 对约 492 个事件做了截断，所以 recall@50 接近整个 haystack，只有 @10 以内是真过滤
- **部分跑批必须用 `--sample N`，不能用 `--limit N`**：LongMemEval_S 按题型成组存放，`--limit 20` 拿到的 20 题**全部是 single-session-user**（实测）。任何按题型的分组数字都不能来自 `--limit`。本节的 500 题是全量，不受影响
- 向量臂的 `vectorTopK` 默认 8 会直接封顶 recall@10，跑向量必须显式 `--vector-topk 50`
- 与 lcm-x 的粒度不同：我们命中的是 **event** 再 dedup 到 session，lcm-x 的 `chunk_vectors` 命中的是 **chunk**。分母不同，`sR@k` 不可直接等同

## 22. 嵌入后端的输入敏感缺陷，以及我们为什么必须按单条降级

### 现象

LM Studio 上的 `text-embedding-qwen3-vl-embedding-8b` 对**特定字符串**稳定返回 HTTP 400：

```
{"error":"invalid_type expected number received nan"}
```

可复现的最小对照（同一个后端、同一时刻）：

| 输入 | 结果 |
|---|---|
| `import x from 'rn-maps';` | **400** |
| ` import x from 'rn-maps';`（前置一个空格） | 200 |
| `. import x from 'rn-maps';`（前置标点） | 200 |
| `import rn` / `import maps` / `react-native` | 200 |

同串连打 6 次全失败，前置一个空格就全成功。所以这是**后端服务的输入敏感缺陷**，不是我们代码路径的问题，也不是网络问题。

### 我们的问题不是这个缺陷，是降级的粒度

`embedTexts` 按 32 条一批发。**一批里只要有一条毒文本，整批 400**，`rankByVector` 抛错，`searchSessionHybrid` 降级回词面 —— **整道题的向量检索全丢**。实测 20 题里 1–3 题（5–15%）被这样拖累。

一条文本的缺陷污染一道题，这个粒度是错的。修法：

1. 批失败时**二分**拆批重试，对数级定位到具体哪几条失败（不是逐条线性重试）
2. 对定位出的毒文本试**一次**前置空格的清洗变体（实测有效）
3. 仍失败的**只跳过那一条**，并计入诊断字段，不让整道题降级
4. **只有全部文本都失败**才抛错 —— 那才是后端真的不可用

### 为什么值得记下来

这不是「换个嵌入模型就好」的问题。任何远程嵌入端点都可能有输入敏感缺陷（分词的边界、Unicode 归一化、超长截断），而**批处理的失败粒度决定了缺陷的爆炸半径**。一个 5% 的输入缺陷不该让 100% 的题降级。

## 23. Layer 2 冒烟（n=5）：单次压缩把 150k 压到 1.2k，答案因此消失

`bench/layer2-qa.mjs`，n=5（head 切片，全是 single-session-user，**不作结论**），答案模型 `balanced-lite`、判分模型 `deepseek-v4-flash-auto`。

| arm | judge CORRECT | string CORRECT | 上下文 token | 单题耗时 |
|---|---|---|---|---|
| full-context（天花板） | 3/5 | **5/5** | 150 469 | 34.9s |
| basic-oneshot | 0/5 | 0/5 | **1 230** | 107.1s |
| lcm-oneshot | 0/3 | 0/3 | **1 648** | 77.0s |
| lcm-agentic | 2/4 | 3/4 | 2 692 | 54.5s |

### 这一节唯一可信的观察

**两个 oneshot 臂的 checkpoint 只有 1.2k–1.6k token，而 haystack 是 150k，预算给的是 16 384。** 也就是说模型自己只写了预算的 7–10%，把 150k 压成了 125:1 —— 答案当然没了。这与生产实测同形（436 194 tok 压到 3 818 tok，114:1）。

而 `lcm-agentic` 在同一 checkpoint 上拿到了 3/4（字符串判分），因为模型可以 search + expand 把原文取回来。**这正是这个架构存在的理由，也是本节唯一没被 n=5 破坏的证据。**

### 我试过「加下限条款让模型别压太狠」—— 没用

在压缩指令末尾加一句「这个 checkpoint 是下一个 agent 能看到的全部内容，请接近预算上限，不要压到丢事实」，在 31k 的 haystack 上：

| 指令 | 输出 token | 比例 |
|---|---|---|
| 原版 | 1 927 | 16.2:1 |
| 加下限条款 | 1 881 | 16.6:1 |

**没有实质变化。** 模型不是被预算逼着压，是自己判断「这段历史大部分是重复闲聊，可以压掉」。加一句「别压太狠」改不了这个判断。

### 这次探测本身是无效的，记下来

我原本想验证「压完的 checkpoint 里还有没有 gold 答案」，用截断到 30k 的 haystack 跑，结果是 gold **不在** checkpoint 里。但那不是压缩的锅：**gold 在第 52 个 session，我的 30k 截断只保留了前 12 个 session**（54 个里）。

所以那次探测什么也没证明。要用它证明「压缩丢了答案」，必须先确认 gold 落在被压缩的区间内 —— 这是任何「压缩导致丢失」的实验的前置条件，忘了它就是测自己的截断。

### 边界

- n=5，head 切片全是 single-session-user，**不能用来排序四个臂**
- 判分模型不是 `gpt-4o`，判分数只作方向参考；字符串判分是下限
- 有 2 次 `fetch failed`、3 次 judge 返回空串被记成「未判」—— 这是**判分链路和重试**的缺陷，正在修，修好前上面那张表的 judge 列不可信（string 列不受影响）
- 单次压缩 ≠ 生产引擎：生产是在增长窗口上**增量**压缩，这里是整段一次性压，所以这一臂是生产保真的**下界**

## 24. 「不能比原版差」到底能比到什么程度

objective 里那句「不能比原版 lcm 更差」需要先说清楚**能比哪一层**，否则很容易拿一个不存在的数字当靶子。

### 原项目自己的结果索引（`lcm-x/benchmarks/METHODOLOGY.md:193-198`）

| 文件 | 层 | 配置 | 状态 |
|---|---|---|---|
| `longmemeval-v2-500q-fastembed.md` | 检索 | 500q, bge-small, per-arm | **landed** |
| `longmemeval-v3-500q-fastembed.md` | 检索 | 500q, bge-small, v3 修正 | **landed** |
| `longmemeval-voyage-100q.md` | 检索 | 100q, voyage-context-3 | **pending** |
| `qa-accuracy-<run-id>.md` | 判分 QA | 500q, CLI judge | **pending** |

**也就是说：原项目的 Layer 2（端到端判分）至今是 `pending`，没有任何已发布数字。**

### 所以我们能比和不能比的东西

| 维度 | 原项目有数吗 | 我们能比吗 | 结论 |
|---|---|---|---|
| Layer 1 词面检索 | 有（`fts` 0.20/0.36/0.204） | **能**，已比 | 我们 0.774/0.874/0.602，同数据集同 query 构造 |
| Layer 1 嵌入检索 | 有（`chunk_vectors` 0.96） | 部分 | 粒度与模型都不同，见 §21，**不可直接等同** |
| Layer 2 判分 QA | **没有（pending）** | **不能** | 没有靶子。我们的 Layer 2 数字只能自证方向，不能声称「不比它差」 |
| 压缩比 / 开销 | 有（但方法论不同） | 部分 | `D2` 那套是自家探针，口径不同 |

### 这条对我们意味着什么

1. **不能说「比原版 lcm 更好」，只能说「在它能比的维度上不差」** —— 词面检索那一条我们领先，但那是**它的 fts 实现**弱，不是它的架构弱（它的强项在嵌入）。
2. **Layer 2 我们做了原项目没做的事**。这不是加分项，是**补空缺**：所以那一层的结论只能是「我们自己测得怎样」，不能是「比它好」。
3. 真正站得住的比较对象是 **`dsh-compaction-basic`** —— 同一个宿主、同一个契约、同一份 config、可 A/B、有已发布的基线行为。objective 里「不能比 dsh 自带压缩更差」这一条，才是能被证据支撑的那一条。

## 25. 一次完整的 agentic 轨迹：薄 checkpoint + 一次检索 = 答对

`bench/results/layer2-probe-agentic.json`，题 `e47becba`（gold: Business Administration），一次完整调用：

```
haystack      148 023 tok
checkpoint      1 669 tok   （预算 16 384，模型只写了 10%）

模型动作：
  lcm_search({"pattern": "graduate|degree"}) → 3 条命中，719 字符
    其中 [seq 530: user] 就是 "I graduated with a degree in Business Administration…"

回答：工商管理学士（Business Administration）。依据 seq 530…
判分：CORRECT（模型判分与字符串判分一致）
```

### 这条轨迹证明了三件事，且都不是推测

1. **checkpoint 薄不影响答对。** 1 669 tok 的摘要里没有这个事实（它是被压掉的），但模型照样拿到了正确原文。这就是「压缩是有损的、指针才是资产」在我们自己手上的实证。
2. **一次检索就够。** 全部工具调用只有 1 次 `lcm_search`，没有 `lcm_expand`。也就是说锚点/查询命中的那一条摘要片段已经足够回答 —— 取回原文是**可选**的第二步，不是必需的第一步。
3. **查询形状的引导真的起作用。** 模型写的是 `graduate|degree`，一个 `a|b` 交替，而不是把问题原句 `What degree did I graduate with?` 贴进去。这正是 0.4.1 改工具描述和零命中提示想让它做的事（同一份数据上，贴原句的零命中率是 99.8%）。**这是一条因果链，不是相关性**：改的是描述，变的是它写出来的 pattern。

### 但它只是 1 题

n=1，题目类型是 single-session-user（最简单的一类：答案就一句自述）。它证明**链路通、机制对**，不证明 20 题上 agentic 一定优于 oneshot。那个数字在跑，跑完单独记。

### 顺带确认的两个数字

- `ratioAsked = 9`（指令要求 9:1），实际 `148 023 / 1 669 ≈ 88.7:1`。再次印证模型不按预算写。
- `meanCheckpointChars = 4 839` 字符 → 1 669 token，即约 2.9 字符/token，是英文为主的典型密度。

## 26. 分片摘要：n=3 的复现**否定**了 n=1 的观察

§23/§25 里有一个诱人的说法：把 150k 的跨度切成 5 片分别摘要在同一总预算下能**保住整段丢掉的事实**。那来自单题（`e47becba`）的一次观察。仪器化后复跑，**结论反了**。

`bench/results/leaf-chunks-20261108-sample8.md`（`--sample 8`，5 题因前置算术不合格被跳过，实得 **n=3**）：

| arm | calls | 输出 tok | 预算占比 | 压缩比 | gold 保住 | 承载 gold 那一片里 gold 在 |
|---|---|---|---|---|---|---|
| A 整段 | 4 | 12 953 | 26.4% | 49.7:1 | **1/3** | — |
| B 分片 | 19 | 17 781 | 36.2% | 31.0:1 | **1/3** | **0/3** |

### 三个必须一起读的数字

1. **总量上分片确实写得多**（17 781 vs 12 953，预算占比 36.2% vs 26.4%），压缩比也更温和（31:1 vs 49.7:1）。**这正是 n=1 时看到的现象，它复现了。**
2. **但保住的事实一样多**（1/3 vs 1/3）。写得更多没有换来更准。
3. **最打脸的一行**：在**承载 gold 的那一片**里，gold 也只出现 0/3 次。也就是说即使把范围缩到「只压这一段相关历史」，模型仍然没把那个事实写进摘要。**丢信息不是「跨度太大压不过来」，是「模型在做摘要这件事时根本没在找事实」。**

### 一个更可能的机制（这次有数据）

`A-whole` 的 12 953 输出 token 里，**7 264 是隐藏 reasoning**，可见摘要只有 5 689。B 分片臂的 reasoning 是 0。也就是说：

- 整段压缩时模型花了 **56% 的输出预算在思考上**，然后写一份很短的摘要；
- 分片时每片都不思考，直接写。

**所以「模型写太短」这个说法要修正**：它写的**可见**摘要短，但它同时在花大预算推理。预算没被浪费，是被用在了看不见的地方。而可见的部分短，是因为模型认定「摘要就该短」。

### 我原来的解读错在哪

我拿单题结果说「分片能让模型写出更多、因此保住更多」。前半句对（写得多），后半句错（保不住更多）。**一个 n=1 的成功案例被我当成了机制解释，而它和最终结论之间根本没有因果关系。**

### 成本

B 分片 19 次调用 / 906 秒，A 整段 4 次 / 261 秒。同样的预算，分片贵 3.5 倍且不更准。**所以这条方向不值得做。**

### 边界

- n=3，5 题被前置算术跳过（gold 不在被压区间、或不具区分度 `gpt4_2f91af09` 的 gold 是 `"23"`，在 haystack 里出现 71 次）
- 判据是 `gold` 字符串字面包含，不是答对；一个事实可能被摘要在语义上保留而字面改写
- 单模型（`balanced-lite`），实际路由漂移过 `agnes-3.0-flash` / `hy3` / `codestral-latest`（结果表的 `resolved model(s)` 列如实记录）

## 27. Layer 2：端到端判分，n=20 —— 这是判决性的那一张表

`bench/results/layer2-qa-sample20-20261108.md`，`--sample 20`（等距抽样，覆盖全部 6 类题型），答案模型 `balanced-lite`、判分模型 `deepseek-v4-flash-auto`（`deepseek-v4.1-flash-1017`），严格串行，9316 秒。

| arm | n | 模型判分 | 字符串判分 | judge 失败 | arm 错误 | 单题 token | 单题秒 |
|---|---|---|---|---|---|---|---|
| `full-context`（天花板） | 20 | **15/20 = 75.0%** | 8/20 = 40.0% | 0 | 0 | 109 350 | 91.6 |
| `basic-oneshot`（dsh 自带压缩） | 19 | **0/19 = 0.0%** | 1/19 = 5.3% | 0 | 1 | 114 618 | 87.4 |
| `lcm-oneshot`（本项目压缩） | 20 | **0/20 = 0.0%** | 0/20 = 0.0% | 0 | 0 | 121 465 | 84.0 |
| **`lcm-agentic`（本项目压缩 + 检索）** | 20 | **14/20 = 70.0%** | **11/20 = 55.0%** | 0 | 0 | 135 354 | 54.6 |

### 这张表说的三件事

1. **只压缩、不给检索，两个后端都是 0%。** basic 0/19、lcm 0/20 —— 在「把 150k 压成一份 checkpoint 然后直接答」这个口径上，**我们不比 dsh 自带压缩差，也不比它好：都归零**。这解释了为什么 §23 里两个 oneshot 臂都 0/5：不是 lcm 的摘要差，是**任何摘要都撑不住 150k → 1.2k 这个压缩比下的问答**。
2. **加了检索之后，lcm 到 70%，天花板的 93%。** 而 basic **没有这个选项** —— 它的 checkpoint 不带 seq 指针，也没有 recall 工具，模型拿到一份摘要之后无从取回。所以「不比 dsh 自带压缩差」在**可用配置**上是 70% vs 0%。
3. **字符串判分上 agentic 反超天花板**（55% vs 40%）。原因不是它更聪明，是它**逐字抄原文**：`full-context` 会写「45 minutes each way.」（带句号、带措辞），agentic 因为 `lcm_expand` 拿的是原文，抄得更准。这说明字符串判分对**表述风格**敏感，不是纯正确性指标 —— 两个判分并列报，不挑好看的那个。

### 工具调用是真的（不是退化）

20 题里 **20 题都调了工具**，平均 2.1 次，最多 6 次（`6456829e` 那道园艺题搜了 4 次 + expand 2 次）。典型序列：

```
e47becba     1 次  lcm_search("graduate|degree") → 719 字符
505af2f5     3 次  lcm_search("coffee|creamer") → expand(seq 80) → expand(seq 79)
6456829e     6 次  lcm_search("tomato|cucumber") → search → expand(430-445) → expand(395-410) → search ×2
```

**模型写的是 `a|b` 交替和单关键词，不是整句问题。** 这是 0.4.1 改工具描述与零命中提示的直接后果 —— 同一份数据集上贴整句的零命中率是 99.8%。

### 为什么天花板本身只有 75%

`full-context` 的 5 道错题里，4 道是**模型答错或拒答**，不是上下文缺失：`3a704032` 答「2 plants」gold 是「3」、`9ea5eabc` 答「Hawaii」gold 是「Paris」、`4dfccbf8`/`982b5123` 直接答 UNKNOWN。也就是说**这个模型在 150k 上下文上的上限就在 75% 附近**，跟压缩无关。agentic 的 70% 已经贴着这个上限。

### 边界（不修饰）

- **n=20**，单模型，每臂一次；20 题里 6 类是等距抽的，不是按类分层配额
- 判分模型不是 `gpt-4o`，模型判分数只作方向参考；字符串判分是下限
- `basic-oneshot` 有 1 次 arm error（网关 400 安全拒绝），已从分母剔除（19 而非 20）
- 压缩是**整段一次性**压，生产引擎是**增量**压；所以 oneshot 臂是生产保真的下界
- `lcm-agentic` 的 agentic 步数上限是 6，20 题里最多用了 6 步（`6456829e` 正好打满）—— 打满的那题答错了
- **与 lcm-x 的 Layer 2 无法对比**：原项目自己那一行至今是 `pending`，没有已发布数字
### 附：§27 的三条口径修正（Layer 2 跑批后审计得出）

跑完 20 题后逐条核查，有三处归因/口径必须修正，否则上面那张表会被读错：

**1. oneshot 的 0% 不是「压缩比太大」，是「锚点清单吃光了输出预算」。**

独立复现一题（`e47becba`，haystack 147 475 est-token，budget 16 384，输出 866 token / 3 685 字符）：

| 分节 | 字符 | 占比 |
|---|---|---|
| 逐字锚点 | 253 | 6.9% |
| 目标与约束 | 231 | 6.3% |
| **已完成** | **2 878** | **78.1%** |
| 未决问题 | 84 | 2.3% |
| 下一步 | 235 | 6.4% |

这一次锚点只占 6.9%，但**另一题实测锚点占 91.3%（4 307 字符 / 258 条），叙述四节合计 369 字符**；还有一题锚点占 99.7%，其余四节**整个缺失**。也就是说分节遵循率本身不稳：锚点节有时吃掉全部预算，有时只剩 7%。

**所以正确的归因是**：oneshot 答 UNKNOWN 的直接原因是 checkpoint 里**不含那个事实**（`e47becba` 的 gold 不在 checkpoint 内，已复现确认），而这不必然等于「压缩得太狠」—— 在锚点占 91% 的那题里，是**输出预算分配**问题。**「压缩损失信息」这个说法把归因搞错了。**

**2. `lcm-agentic` 的字符串判分被语言漂移系统性低估。**

agentic 臂的答案 **11/20 含中文**，其余三臂 **0/20**（gold 全英文）。例：`efc3f7c2` gold `30 minutes`，答「30 分钟。」→ `string=false` 但 `judge=CORRECT`。所以 `string=0.55` 不能与其它臂并列读，只能臂内自比。

**3. judge 对长答案更宽松，judge 列不是臂间同一把尺。**

`string=false` 但 `judge=CORRECT` 的题数：`full-context` **7 题**、`agentic` 3 题、两个 oneshot **0 题**。典型：gold `2` 答「Dr. Thompson…and Dr. Smith」、gold `3` 答「Three」、gold `8` 答「5 tomato and 3 cucumber plants」全判 CORRECT。**答案越长越吃宽松度**，所以 full-context 的 75% 里有这部分水分。judge 方向可用，不能当精确刻度。

**另外两处**：

- `meanTokens` 一列里 **97% 是压缩成本**（basic 110 972/114 618），不是答题成本；且含 judge token；且 `basic-oneshot` 是 n=19（1 次网关 400 出分母）。**臂间 n 不同，百分比不能直接比大小。**
- `agentic` 有 **2 例是协议故障被计成 WRONG**（`982b5123` 把工具调用当文本吐出、`6456829e` 撞 max-steps=6），应单列而不并入错误率。
### 修法与效果：把「先砍叙述」改成「合并重复，四节不许省」

`ANCHOR_RULE` 原文写的是「这一节宁长勿短；预算不够时**先压后面四节**」。20 题实测里模型照做了：一题锚点占 **99.7%** 且其余四节**整个缺失**，另一题锚点占 **91.3%**。

改成「后面四节**必须都有内容**，一节都不许省」+「锚点太多就**合并重复**（同一路径反复出现只写一次），而不是删小节、也不是删锚点」。

同一题（`e47becba`，同 haystack、同目标 16 384）改前改后：

| 分节 | 改前 | 改后 |
|---|---|---|
| 逐字锚点 | 253 字符 / 6.9% | 3 059 字符 / **36.7%** |
| 目标与约束 | 231 / 6.3% | 1 688 / **20.2%** |
| 已完成 | 2 878 / 78.1% | 2 925 / 35.1% |
| 未决问题 | 84 / 2.3% | 262 / 3.1% |
| 下一步 | 235 / 6.4% | 402 / 4.8% |
| **输出总量** | 866 tok | **2 620 tok** |

**五节都在、分布健康了，输出量也上来了**（866 → 2 620 token，因为不再有硬上限，模型敢写）。

**但 gold 仍然不在 checkpoint 里。**

## 29. 借 lcm-x 的断言结构改造「用户事实」节

用户提示「参照 hermes-lcm-x 怎么处理，如果它更好就用它的」。读了它的 `assertion_extraction.py` / `assertion_store.py`（共 2 211 行），它对这个问题的处理确实更严谨，**已借用**。

### lcm-x 的做法（`assertion_store.py:37-58`）

它不靠摘要承载事实，而是**抽取结构化断言**，每条有：

```
source_span_start / source_span_end / source_quote   精确到字符偏移的原文引用
subject_key                                          canonical namespace:value（user/person/place/organization/object/event/project/document/account/assistant/conversation）
predicate_key                                        canonical 小写点分谓词
object_value + value_text                            结构化值 + 简洁原文文本
kind                                                 fact|event|preference|recommendation|commitment|action|status|quotation
polarity                                             positive|negative|unknown
strength / scope_key / event_at / valid_from / valid_to
relations                                            cancels|confirms|contradicts|narrows|reverses|supersedes|weakens|fulfills|quotes
```

三个设计点值得直接借：**① `kind` 是封闭枚举**（8 种），每一种都对应一类会被问到的东西；**② `polarity` 独立于值**，所以「喜欢 A、不喜欢 B」有地方放；**③ `source_quote` 必须是精确子串**，天然禁止翻译和改写。

### 我们借用的部分

`## 用户事实` 从「写句子」改成**带类型的事实行**：`主体.谓词 = 值 | 类型`，类型只用 lcm-x 那 8 种里对得上问答的 7 种（`fact` / `number` / `time` / `event` / `preference` / `status` / `commitment`），`preference` 带 `+`/`-` 极性，`event` 每条单独一行带 `1)` `2)` 次序，值**必须原文语言逐字**。

### 顺带发现的两个回归（都已修）

1. **把锚点节加宽成「短事实 `事实: 值`」是错的。** 实测输出变成中文散文：「用户祖母于 1 月 15 日 去世，几天后举行了葬礼。」—— 锚点节的唯一价值是**可粘贴进 `lcm_search` 的字面串**，写成句子就毁了这个性质。已恢复为**纯词表**，事实全部移到第二节。这是借用 lcm-x 的结构之后才看清的：它的 `source_quote` 必须是精确子串，所以它的抽取**不可能**退化成散文。
2. **锚点清单需要上界。** 不加界时模型写了 13 837 字符的锚点，然后**一口气写完 6 节**（那次 `finish=stop`）；但另一次只写了 7 722 字符就停在**一个**小节（锚点），其余五节没有。同一指令、同一题，行为差异极大。加了「最多 120 行，唯一性优先、具体优先」的界，理由是**日志留着所有字符串、`lcm_search` 能找到任意一个**，所以穷举清单是在重复日志，还把「搜索也救不回来」的那部分（事实行）挤掉。lcm-x 同样有界（每条源最多 100 条断言、源文本 24 000 字符）。

### 测量状态：不完整，如实记

用「压缩 → 只给 checkpoint 答题 → 字符串判分」测了 15 组配对失败里的一部分，**指令改到一半就停了**，所以下面的数不能当结论：

| 题 | 改前 | 改后 |
|---|---|---|
| e47becba（`Business Administration`） | UNKNOWN | **答对** |
| 0ea62687（`2` mpg） | UNKNOWN | **答对** |
| 95bcc1c8（`10` 个喜剧演员） | UNKNOWN | **答对**（仅在类型化事实行那版） |
| efc3f7c2（`30 minutes`） | UNKNOWN | 仍 UNKNOWN |
| 6613b389 / 06db6396 / 7e00a6cb | UNKNOWN | 仍 UNKNOWN |

**3 题由不可答变可答、4 题仍不可答**，n 太小且中途改过两次指令，**不能据此宣称改进**。要判定得把整套指令固定下来、对 15 题跑一次完整的 before/after（`bench/acon-loop.mjs --instruction-module=bench/snapshots/summarize-head.mjs` 就是为此准备的）。

**一条更硬的观察**：`95bcc1c8` 的 gold `10` 在改前的锚点表里就有（单独一行），模型仍答 UNKNOWN；改成类型化行 `user.watched_amateur_comedians = 10 | number` 之后才答对。**同一个值，有没有谓词和类型，决定它可不可答。** 这一条比任何聚合数字都有说服力，且在两种形态上各测过一次。

## 30. 为什么 lcm-x 更好：不是提示词，是「压缩当索引」而不是「压缩当替换」

用户问「如果效果没有 lcm-x 好，就看看它怎么做的」。读了它的 `engine.py` / `compaction.py` / `config.py`，结论是**它的差别不在摘要指令，在架构**。

### 硬证据：它没有「只给摘要」这种模式

`engine.py:10362` `_assemble_context` 的注释就写着组装结构：

```
[leading anchors: system and, when proven, the sole real user]
[highest-depth summary nodes first, then lower]
[fresh tail messages]
```

也就是说模型每次看到的上下文 = **多层摘要节点（深先浅后）+ 新鲜尾部**，而不是一份压平的摘要。再加上检索工具默认可见 13 个（共 16 个）。**它根本不构造「只有摘要」的配置。**

### 两边的默认参数对照（`config.py`）

| | lcm-x | 本插件 |
|---|---|---|
| 触发 | `context_threshold = 0.75` | `thresholdRatio = 0.8`（与 basic 相同） |
| 叶块大小 | **`leaf_chunk_tokens = 24 000`**（再被 0.4×ctx 夹住） | **整段可压前缀一次压完** |
| 叶目标 | **2 000 token** | 跨度的 12%（上限 16 384） |
| 合并 | **`fanin = 4`，`incremental_max_depth = 3`** | 无显式 fanin；吸收旧 checkpoint 时 depth+1 |
| 新鲜尾部 | `fresh_tail_count = 24` / 24 000 token | 保留尾部按 `retainRatio` |
| 上下文来源 | **多层摘要 + 尾 + 检索** | checkpoint + 尾（+ agentic 臂才检索） |

一句话（我自己上一轮的笔记里就有这句，这次才真的用上）：**标准压缩把压缩当替换，LCM 把压缩当索引化** —— 摘要降级为「缩小搜索范围」的指针，不是「替代原文」的唯一副本。

### 这直接解释了我们那张表

| 配置 | 对应 lcm-x 的什么 | 我们测到 |
|---|---|---|
| `lcm-agentic` | **lcm-x 的常态**（摘要 + 检索） | **70%**（天花板 75%） |
| `lcm-oneshot` | **lcm-x 没有这个模式** | 0% |
| `basic-oneshot` | 同上 | 0% |

所以「不如 lcm-x」这个判断**在可比的配置上不成立** —— 我们的 agentic 臂就是它的常态形状，70% 已经贴着天花板。**oneshot 那个 0% 没有 lcm-x 的对应物可被比下去。**

### 但它确实指出了一个真实的架构差距

我们每次压缩产出**一个** checkpoint 节点（`compile()` 返回 `entries: [{ seq, text, kind: "checkpoint" }]`），lcm-x 产出**多个**、按 depth 组织、`fanin=4` 合并。我们的 `deriveDag` 能**推导** depth，但**从来没生产过多个叶**。

这是下一步该做的事，而且和之前被否掉的「分片摘要」不是同一件事：那次是「切块、各自压、拼成一份」，拼完还是一份，检索目标还是一个；正确做法是「切块、各自压、**各自成为一个 surface 节点**」，这样检索有多个目标、DAG 有东西可合并。**我之前的实验测错了对象，所以结论「分片无用」只对「拼成一份」那种做法成立。**

### 指令层面的改动：保留有证据的，停止没有证据的调参

这一轮在 oneshot 指令上改了很多，其中**有证据支持的只有三条**，其余都是没测出差异的调参：

1. **值必须原文语言、逐字**（`76d63226`：译成中文时错，逐字 `55-inch` 时对）
2. **事实要带谓词和类型**（`95bcc1c8`：`10` 单独一行时答不出，`user.watched_amateur_comedians = 10 | number` 才答得出）
3. **给 provider 一个够高的上限**（无上限时被 provider 默认值截断：7 734 字符只剩锚点节；显式 32 768 时 8 817 字符六节齐全）

最新的 15 题可答性（三处修复都在）：**2/15**，改前 0/15。**但其中 5 题仍然只写出一个分节**（截断或模型提前收尾），所以这个 2/15 是下界，不是这套指令的真实上限。

**停止调 oneshot 指令**：它不是我们被比较的配置，继续调它是在优化一个 lcm-x 不参与的项目。

**7/7 全部 6 节齐全、finish 全是 stop、承载 gold 的那片确实带着 gold。**

### 和整段一次压的对照

| | 整段一次压 | 7 叶分别压 |
|---|---|---|
| 模型调用 | 1 | 7 |
| finish | 多次出现 `length` 截断 | **7/7 全 stop** |

### 代价（要如实说）

- 调用数从 1 变成 ⌈span/24k⌉。147k 是 7 次；生产 436k 会是 ~19 次。
- checkpoint 总量变大：37 638 vs 最多 13 837 字符（约 2.7 倍）。但相对原文仍是 147k → ~12k token（12:1），与 lcm-x 的叶目标一致。
- **多次调用之间是串行的**，总墙钟变长。

### 还没测的

- 7 叶拼起来的 checkpoint 上答题的**可答性**（结构对了不等于答得出）
- `deriveDag` 能否正确识别 7 个叶节点的 depth（现在还没有多叶的真实日志可供它跑）
- fanin 合并：lcm-x 在 4 个同深度叶之后触发上一层合并，我们还没有这个策略，叶会一直平铺
### 可答性：同样的 4 题，整段 0/4 → 叶块 4/4

用同一批 4 题（都在 15 组配对失败里，改前全答 UNKNOWN），只换压缩方式：

## 33. 为什么原程序（lcm-x）能过，我们过不了：一个具体题的解剖

拿 `00ca467f`（multi-session，问「三月去了几次医生」）把它摊开，答案就清楚了。

haystack 49 个 session，含 appointment 相关字样的一共 9 条，散在 s1 / s6 / s13 / s37 / s42。**gold 是 2**，而真正算数的只有两条：

```
s1  user: follow-up appointment with my orthopedic surgeon, Dr. Thompson, on March 20th,
         and it was a relief to hear that my knee is healing well.        ← 已发生 + 三月 → 算
s42 user: I finally went to see my primary care physician, Dr. Smith, on March 3rd      ← 已发生 + 三月 → 算
```

其余七条都是**干扰项**，而且干扰的方式各不相同：

```
s1  user: I'm considering scheduling an appointment with Dr. Patel…        ← 只是「在考虑」，没发生
s13 user: I had an appointment with my primary care physician, but…       ← 没日期，凭上下文是更早
s6  assistant / s37 user                                                  ← 八竿子打不着
```

### 这一步需要什么能力

答对这题 = **对九条原文逐条判断「有没有发生在三月」再数**。判据是「已发生 / 在考虑 / 无日期」，而这三个判据**只有拿到原句才判得出**。

### 所以 lcm-x 为什么能过

**因为它从来不让摘要去回答这个问题。** 它的设计是：

1. **原始消息永不删除**（append-only，`lossless means lossless`），摘要是**索引**不是**替代品**
2. 答题时对原始 store 做检索（13 个工具默认可见），拿到那九条，**自己逐条判**
3. 它的断言库还额外把 `kind` / `polarity` / `event_at` / `valid_from` / `cancels` 分开存，所以「在考虑」和「发生过」在库里就是不同的行

**换句话说：原程序能过，是因为它把「需要逐题判断」这件事留到了答题时做；我们 oneshot 臂试图在压缩时预先把答案算好。**

而压缩时**不知道会问什么** —— 不知道要按三月筛、不知道要区分「在考虑」和「已发生」。任何指令都补不上这个信息差。

### 这解释了我们那张表，也定死了结论

| 配置 | 有没有「答题时看原文」 | 结果 |
|---|---|---|
| `lcm-agentic` | **有**（`lcm_search` + `lcm_expand` 取原文） | **70%**（天花板 75%） |
| `lcm-oneshot` | 无 | 0% |
| `basic-oneshot` | 无 | 0% |
| lcm-x | **有**（检索原始 store） | 它的常态 |

**所以 oneshot 那个 0% 不是「我们比 lcm-x 差」，是「这个配置在所有后端都会归零，包括原程序如果关掉检索」。** 而我们真正要对齐的那个配置（agentic）已经是 70%，贴着天花板。

### 对指令改动的意义

这一轮改的「事件行要带日期和状态」**方向是对的但不够**：它能让 checkpoint 里区分「已发生/已取消/计划中」，把九条干扰压到接近两条；但**它仍然要猜题目问的是哪个窗口**。在 agentic 配置下这条规则价值更大，因为检索拿回原文后，checkpoint 里的事实行能帮模型定位到「三月」这个窗口。

**结论：不再指望 oneshot 追平。** 要做的是把 agentic 那条路做扎实（检索命中率、`lcm_expand` 取原文的粒度），以及保证生产环境默认就是这个形状。

## 34. 复盘：拿 LCM 的六步流水线逐条对，然后改一处

用户指出「再复盘一下 lcm 的设计思路和行为准则再行动」。读了 `lcm-x/docs/architecture.md`，它把设计写成六步流水线，逐条对照如下。

### LCM-X 的六步（原文）

```
1. Ingest   - persist each message in SQLite with FTS metadata
2. Compact  - summarize older messages outside the fresh tail into D0 leaf nodes
3. Condense - merge same-depth nodes into higher-depth summaries
4. Escalate - shrink oversize summaries from detailed to bullets to deterministic truncate
5. Assemble - combine system prompt, highest-depth summaries, and fresh tail
6. Retrieve - use LCM tools to drill into compacted history
```

外加一条行为准则（写在它的 `AGENTS.md` 不变量里）：**prefer degraded coverage, a safe no-op, explicit warnings, or a tracked repair over destructive recovery**。

### 我们逐条对

| 步 | LCM-X | 我们 | 判定 |
|---|---|---|---|
| 1 Ingest | SQLite + FTS，append-only | dsh 的会话日志本身就是 append-only，我们只读它、不删 | ✅ 等价（由宿提供） |
| 2 Compact | 叶块切 D0 | `leafSpanTokens` 24 000，叶从最老节点起 | ✅ 本轮补上 |
| 3 Condense | 同深度合并成更高层 | **没有**。我们只是反复压前缀，depth 靠吸收自增，没有同深度合并 | ❌ **仍缺** |
| 4 Escalate | detailed → bullets → 确定性截断 | 原来是「重试一次然后抛错」 | ❌ → ✅ **本轮修** |
| 5 Assemble | system + **最高层摘要优先** + 新鲜尾 | 一个 replace 换成一个节点，组装是隐含的 | ⚠️ 部分（受单条替换约束，见 §21） |
| 6 Retrieve | 13 个工具 | `lcm_search` + `lcm_expand` | ✅ |

### 第 4 步是我这段一直在踩的坑

LCM 的三级阶梯原文：

```
Level 1 (Normal):    LLM summary preserving details
Level 2 (Aggressive): LLM bullet-point summary at half the token budget
Level 3 (Fallback):   Deterministic truncation — no LLM, guaranteed convergence
```

**我们原来是：超长了 → 重试一次（同预算、加一句硬约束）→ 还超长就抛 `SUMMARY_NOT_SHRINKING`。** 这直接违反了「宁可降级覆盖也不要失败」：一次写超长变成整次压缩失败、整段跨度失去摘要，而且下一步还会再犯。真引擎日志里反复出现的 `summary body is still not shorter…`、`summary truncated at the token cap`、`一起 compaction failed` 都是这一条的后果。

### 改法（已实现）

```
Level 1  正常生成（目标 budget）
Level 2  超长 → 重试用一半预算 + 硬约束文案
Level 3  仍超长 → 确定性截断：从尾部按行切到放得下，不调模型，保证收敛
```

两处细节是必须的，否则阶梯不收敛：

1. **截断要预留 header 的 token。** 收缩闸比的是**整条 entry**（header + 正文），我第一次没预留，100 token 的界加 30 token 的 header 又超了，等于截断白做。加了 `headerTokens()` 先扣。
2. **注记要能缩短。** 完整注记约 40 token，在小预算下它自己就吃掉一半；改成「放得下就用完整注记，放不下用 `[truncated; see lcm_search]`，再放不下就不带注记」，最后再加一个**按字符硬收敛**的循环兜底 —— 否则「保证收敛」只是口号。

**为什么截断安全**：锚点节是被刻意排在最前面的（§19 的 0/14 vs 2/14 那组数据），所以从尾部截断**先丢叙述、后丢锚点**。这正是当初把锚点前置的理由，而我之前从没真正用上它。

### 复盘还指出的一个方法论错误

LCM 的立场是「摘要是索引，不是替代品」（`Raw messages remain source truth. Summaries … are derived layers`）。**按这个立场，摘要文本的措辞根本不值得我花那么多轮去调** —— 指针和可检索性才是资产。我在 §29–§33 里反复改摘要指令，方向是偏的；真正缺的是第 3 步（同深度合并）和第 4 步（降级阶梯）。

### 剩下的真实差距

只剩第 3 步：**同深度叶合并成更高层**。现在叶会一直平铺，`deriveDag` 能算出 depth 但没人触发合并。lcm-x 是 `fanin = 4`。这一条要改的是「压缩时优先选同深度的相邻叶来合并」，而不是现在的「从最老节点顺序切」（**本轮已实现，见 §36**）。

## 35. 「压力超了却不压」不是 bug，但日志必须说出来

在真 dsh 会话里看到一次：`pressure: measured=14208 threshold=13616`，超了阈值，却**没有任何压缩**，也没有报错。这看起来像引擎坏了。

拿真实会话做探针（`Session.create` + 真 `TokenMeter` + 真 `selectCompactableRange`）复现：

```
surface 17 个节点，实测总量 14 372，retainTokens 4 472
引擎参数 (0, 512, 24000, 4) -> 8-8        ← 只选出一个节点
```

那个节点 **233 token**，而跨度下限守卫要求 `spanTokens > 2 × summaryFloorTokens = 1024`，所以**返回 null 是正确的**：压一个 233 token 的节点，预算被钳到 512，数学上不可能缩小。

**真正的原因是 `retainRatio` 在这条小会话里吃掉了几乎全部可压材料**：13.7k 的会话保留 4 472 token 的尾巴之后，前缀只剩一个 233 token 的节点。这不是退化，是「没有值得压的东西」。生产会话（几十万 token）不会出现这种情况。

### 改了什么

行为不改（返回 null 是对的），**加了一行诊断**：

```
pressure declined: 14372 >= 13616 but no range passed the guards
  (retain=4472 floor=512 leaf=24000 fanin=4)
```

理由：之前「超阈值但无可压区间」和「压缩坏了」在日志里长得一模一样。这一轮我为此花了十几分钟做探针才排除掉 bug —— 而这行字本该直接告诉我。

### 一条方法论教训

探针的价值在这里体现得很清楚：**用真实会话 + 真 meter + 真选择器跑一次，两分钟就能把「疑似 bug」变成「预期行为」**，比读代码猜快得多。以后再遇到「应该有动作却没有」，先做这个探针。

### 改法：不是加日志，是加「保持」（照 lcm-x 的 `_no_progress_hold`）

用户指出只加一行日志是治标。查了 lcm-x 的实现：

```python
# engine.py:2204
def _no_progress_hold_active(self, *, managed_scope=False):
    """#651: never latches; it ends at its time (a stored leaf clears it in compress())."""
    if time.monotonic() < self._no_progress_hold[0]:
        return True
```

```python
# engine.py:2527 — the gate consults it BEFORE doing any work
return tokens >= self.threshold_tokens and not self._sweep_budget_hold_applies(tokens, managed_scope=True)
```

配套还有 `_zero_leaf_streaks`（#1162：连续「超阈值但没存下叶」的计数）。**四个要点**：① 保持是**时间截止**的，不会永久闩死；② **存下一个叶就清除**；③ 在**做任何工作之前**判定，所以不会每步重新计价；④ 手动/紧急路径豁免（`_sweep_budget_hold_applies` 明确不放行超过 survival ceiling 的调用）。

我们原来是**每一步都把整条评估重跑一遍**：meter 测量 → 模型信息查询 → 区间选择 → 拒绝 → 记日志，然后下一步再来一遍。**真正的问题在于：一个已经有答案的问题被每一步重新问了一次，仅加日志并不能解决。**

### 现在的实现

```js
const stall = this.stallBySession.get(session.id);
const grew = measurement.totalTokens >= stall.tokens + this.config.leafSpanTokens;
if (!grew && Date.now() < stall.until) return null;
```

- **arm**：区间选择返回 null 时记 `{tokens, until: now + stallCooldownMs}`
- **release**：存下一个 checkpoint、**长了另一整片叶那么多新内容**、或超过 `stallCooldownMs`（默认 60 s）
- **exempt**：`requireBelowThreshold` 为真时永不保持 —— 那是手动 `/compact` 和模型切换；操作员要的是答案，「没东西可压」就是答案
- `stallCooldownMs: 0` 完全关闭保持

**为什么用「长了一片叶」而不是「长了任意内容」**：叶块大小正是「多出来一块值得单独压的东西」的最小单位。任意增长会让保持形同虚设，纯时间截止又可能让本该压的东西拖到 60 秒后。这个阈值和 `leafSpanTokens` 同源，不是新拍的数字。





### 这与 §26「分片无用」的矛盾怎么解释

§26 测的是「切块 → 各自压 → **拼成一份** 16384 预算」，每片预算只有 3276，而且拼完还受同一个输出上限约束。这次是「切块 → 各自压 → **各自 2048 目标、各自 finish=stop**」，每片都在自己的安全区间里写完。**两次的区别是「每片是否拥有完整的目标」和「是否被同一个输出上限掐住」，不是「切不切」。** §26 的结论只对「共用一个预算」那种做法成立。

## 28. 去掉 maxTokens 之后暴露的第四个问题：模型会写超，撞收缩闸

用户指示「不要设 max token 预算」，照做之后在真引擎上看到一个新的失败模式（`/tmp/lcm-fresh-debug.log`，全新 profile）：

```
[dsh-lcm] engine: summarize span=6 seqs=32-37 shadowedTokens=1517 budget=512
[dsh-lcm] engine: summarize done tokens=2438 ratio=0.62
[dsh-lcm] engine: step compaction failed: compiled checkpoint is not smaller than the shadowed content
                  (1837 estimated framed tokens >= 1517)
```

**目标 512，模型写了 2 438（4.8 倍），比被压的原文还长**，于是收缩闸（`framed < shadowed`）把它拒了 —— 闸是对的，这是一次**浪费掉的模型调用**。

### 为什么会这样

去掉上限之后，「写多长」完全由模型自己判断。它有时写得比目标短（另一题 1 039 → 549，ratio 1.89，正常），有时写得远长于目标。**指令里的「Aim for roughly N」是软约束**，模型可以不听，而收缩闸是硬约束，所以失败落在闸上。

### 这不算「不该去掉上限」

设上限的时候，这个场景的失败形态是「`finish=max-tokens` 且正文为空」（推理吃光预算）—— 一样是浪费一次调用，而且**更糟**：上限把输出截断在目标处，模型还没开始写就没预算了。现在至少模型写出了完整的东西，只是太大。

### 该怎么修（未做，已排队）

收缩闸拒绝之后**重试一次**，并在那一次请求的指令里把「必须比原文短」写成硬要求（现在的措辞只说了目标值）。这是合法重试：失败不是确定性的（输出长度每次不同），与 `max-tokens` 那种确定性截断不同。

**成本上界**：最坏 2 次调用；正常路径 1 次。

### 顺带一个观察

同一份日志里第一次压缩 `1039 → 549`（ratio 1.89）**成功了**，但紧接着报 `still above threshold after 2 compaction attempts`。那不是 bug —— 我把 `thresholdRatio` 压到 0.001（阈值 256 token）来逼出压缩，压完当然还在 256 以上。**正常配置触发点是 0.8×窗口**，不会出现这种追击。
